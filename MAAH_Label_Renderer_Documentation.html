Internal Technical Documentation

MAAH Label Renderer

Complete V1 reference for installation, development, standalone deployment, SVG template preparation, JSON mapping, artwork defaults, Avery sheet geometry, printer calibration, validation, PDF generation, build behavior, recovery and day-to-day production use.

1. Purpose & Scope

MAAH Label Renderer is a local Windows application that transforms a normalized MAAH SYSTEM label-job JSON file and a reusable SVG artwork template into printable Avery A4 sheet layouts and PDF files. The renderer is deliberately separated from the business database: it consumes exported data instead of connecting directly to Google Sheets, Apps Script, Odoo or any other ERP.

JSON = production dataProduct, lot, label and print information supplied by MAAH SYSTEM.
SVG = artworkReusable transparent design containing explicitly identified dynamic text fields.
Mapping = data bindingConnects each dynamic SVG text ID to one scalar JSON path.
Label format = physical geometryDefines Avery label size, rows, columns, margins, pitch and calibration defaults.
Artwork settings = visual placementControls uniform artwork scale, solid background color and background bleed.
Inkscape = PDF engineThe renderer produces SVG; Inkscape CLI performs the final SVG-to-PDF conversion.
V1 is intentionally narrow: reliable label rendering, not ERP functionality, not a graphical label designer and not a direct database client.

2. Architecture

MAAH SYSTEM ↓ Normalized Label Job JSON + Transparent Square SVG Artwork + Saved SVG-ID → JSON-Path Mapping + Artwork Settings + Avery Format Geometry ↓ Validation ↓ Dynamic Artwork SVG ↓ Background + Bleed + Uniform Artwork Scale ↓ A4 Avery Sheet SVG(s) ↓ Inkscape CLI ↓ Print PDF(s)

3. Development Installation & Environment Setup

This section is for a development or maintenance computer where the source project is edited and rebuilt. The compiled standalone application does not require Python; see the next section for standalone deployment.

3.1 Supported / tested environment

The current V1 project has been developed and tested on Windows using 64-bit CPython 3.14 and PyInstaller. The exact Python installation path is not part of the application contract; the project uses its local .venv once created.

3.3 Install Python

Install an official 64-bit Python build for Windows. During installation, ensure that the standard Tcl/Tk components are included. After installation, verify Python from PowerShell: 

python --version
python -c "import sys; print(sys.executable); print(sys.version)"

If python is not on PATH, the Windows Python launcher can also be checked:

py --version

3.4 Verify Tkinter before continuing

python -c "import tkinter; print('Tkinter OK - Tk', tkinter.TkVersion)"

A version number confirms that the GUI dependency is available.

3.5 Create the project virtual environment

Open PowerShell in the project root:

python -m venv .venv
.\.venv\Scripts\Activate.ps1

If PowerShell blocks local activation scripts for the current session:

Set-ExecutionPolicy -Scope Process Bypass
.\.venv\Scripts\Activate.ps1

Verify that the active interpreter is the virtual environment:

python -c "import sys; print(sys.executable)"

3.6 Install build dependency

python -m pip install --upgrade pip
python -m pip install pyinstaller
python -m PyInstaller --version

3.7 Verify project Python modules

From the project root with the virtual environment active:

python -c "import json_loader, svg_loader, mapping_store, template_settings_store, validator, renderer, label_formats, sheet_layout, inkscape_exporter; print('Project modules: OK')"

If this fails, check that all project .py files are present in the same project root as app.py.

3.8 Install and verify Inkscape

Install Inkscape normally on Windows. The renderer can use an explicitly configured executable path or attempt to discover Inkscape from PATH and common Windows install locations.

Typical direct verification:

& "C:\Program Files\Inkscape\bin\inkscape.exe" --version

If Inkscape is available on PATH:

inkscape --version

An explicit path can be set in config.json:

{
  "schemaVersion": "1.0",
  "appVersion": "1.0.0",
  "inkscape": {
    "executablePath": "C:\\Program Files\\Inkscape\\bin\\inkscape.exe"
  }
}
The current artwork Scale / Background / Bleed defaults are controlled by template_settings.json, not by config.json. If older defaults keys still exist in config.json, they are not the authoritative visual-default system in the current V1 architecture.

3.9 Run the source application

python app.py

A production computer does not need Python, the virtual environment, PyInstaller, VS Code or the source .py files. It does need the complete PyInstaller distribution folder and Inkscape if PDF generation is required.

Do not distribute or move only MAAH Label Renderer.exe. V1 is intentionally built with PyInstaller --onedir, so the executable depends on the rest of the distribution directory, especially _internal/ and the external configuration files.

4.2 Install Inkscape on the production computer

Without Inkscape, the application can still load and validate its own inputs, but final PDF export cannot complete. Install Inkscape and verify the executable path.

4.3 Fonts are an external visual dependency

Any font used by dynamic SVG text must exist on the computer performing the Inkscape export. Missing fonts can change text metrics and appearance. Static decorative text may be converted to paths in the SVG when appropriate, but dynamic field_* text must remain real SVG text so the renderer can replace its content.

4.4 First standalone test

  1. Start MAAH Label Renderer.exe.
  2. Browse a JSON job; the browser should open in input/.
  3. Browse an SVG; the browser should open in templates/.
  4. Confirm a saved mapping loads or create one.
  5. Validate the job.
  6. Generate labels.
  7. Confirm SVG and PDF outputs appear in output/.
  8. Close and reopen the application to confirm persistent settings remain available.

6. SVG Artwork Standard

6.1 Required conceptual format

The preferred master artwork is:

Format: SVG
Aspect ratio: 1:1
Background: transparent
Preferred viewBox: 0 0 512 512
Dynamic text: real SVG <text> elements
Dynamic IDs: unique and beginning with field_

512 × 512 is a design coordinate system, not a physical print size. Physical millimeters are applied later by sheet_layout.py using the selected Avery format.

6.2 Transparent artwork is deliberate

Do not bake the production background or bleed into the master artwork. V1 generates a solid background separately, which allows the same artwork to be reused with different background colors and bleed values without maintaining duplicate SVG files.

6.3 Embedded assets

For operational reliability, embed raster images and other external assets inside the SVG whenever possible. Linked files can break when the template folder is copied to another workstation.

6.4 Text and fonts

Dynamic fields must remain text. If they are converted to paths, the renderer can no longer replace their content. Static logos or decorative text may be converted to paths if desired. Fonts used by dynamic text should be installed on every computer that performs PDF export.

7. SVG Dynamic IDs — Detailed Guide

SVG IDs are the core link between visual artwork and production data. The renderer does not search for visible words such as “Product Name” or “Weight.” It searches the SVG XML for <text> elements whose id begins with field_.

7.1 Naming rule

field_<meaningful_name>

Recommended style:

field_product_name
field_frozen_status
field_net_weight
field_lot_id
field_label_id

Use lower-case snake_case after field_. This is not only cosmetic: consistent IDs make mappings readable and maintenance much safer.

7.2 Concrete current JSON examples

Given a job containing:

{
  "labelId": "LAB-0012",
  "lot": {
    "lotId": "L-261006-P001-001",
    "productName": "Chicken Curry"
  },
  "product": {
    "productId": "P001",
    "productName": "Chicken Curry",
    "labelName": "Chicken Curry",
    "frozenStatus": "Tiefgefroren",
    "netWeightG": 500,
    "netWeightText": "500 g"
  }
}

A template can use:

SVG text IDJSON pathRendered example
field_product_nameproduct.labelNameChicken Curry
field_frozen_statusproduct.frozenStatusTiefgefroren
field_net_weightproduct.netWeightText500 g
field_lot_idlot.lotIdL-261006-P001-001
field_label_idlabelIdLAB-0012

7.3 What the SVG XML should conceptually contain

<text
    id="field_product_name"
    x="256"
    y="180"
    text-anchor="middle">
  <tspan>PRODUCT NAME</tspan>
</text>

The placeholder text itself is irrelevant. The renderer uses the ID. At render time it replaces the text content while preserving the existing element's position and styling.

7.4 How to assign IDs in Inkscape

  1. Create the text object normally and style it exactly as desired.
  2. Select that text object, not the surrounding group.
  3. Open Inkscape's object properties / object ID controls or XML editor.
  4. Set the object ID to a unique value beginning with field_.
  5. Save the SVG.
  6. Load it in MAAH Label Renderer and confirm the ID appears in the Mapping section.
The ID must belong to the actual SVG <text> element. Assigning field_product_name to a surrounding <g> group, rectangle or path does not make that object a dynamic text field.

7.5 Unique IDs are mandatory

Do not duplicate a dynamic ID in one SVG. Two separate objects cannot both be field_product_name. The SVG loader validates ID uniqueness because ambiguous IDs would make deterministic replacement impossible.

7.6 Dynamic text must not be converted to paths

Inkscape can convert text into vector paths. That is acceptable for static artwork but not for dynamic fields. Once converted to a path, it is no longer a <text> object and is therefore intentionally ignored by dynamic-field detection.

7.7 Tspan behavior

SVG text exported by Inkscape often contains one or more <tspan> children. The V1 renderer writes the resolved value into the first tspan and clears additional tspans to avoid leaving stale placeholder fragments behind. For that reason, design each dynamic field as one logical text value rather than manually splitting a single dynamic value across many tspans.

7.8 V1 does not auto-fit long text

The renderer preserves the template's font size and styling. It does not automatically shrink text to fit. A product name that is much longer than the design placeholder can overflow its intended area. Template design and upstream label text should therefore be tested with realistic maximum lengths.

7.9 Static text is unaffected

Text that does not use a field_ ID remains static. It can have a normal Inkscape ID, another custom ID or no meaningful custom ID at all.

7.10 Filename uniqueness matters

Both mappings.json and artwork-specific entries in template_settings.json are keyed by the SVG filename, not by the full folder path. Therefore operational template filenames must be unique. 

GOOD:
maah_front_default.svg
maah_back_default.svg
kohitsune_front_default.svg

RISKY:
templates/brand_a/front_default.svg
templates/brand_b/front_default.svg

In the risky case, both files share the key front_default.svg and could unintentionally share/overwrite saved mapping or artwork-setting configuration.

7.11 Changing IDs after a mapping is saved

If an SVG template is edited and field_* IDs are renamed, added or removed, its saved mapping may no longer match the artwork. Load the revised template, inspect every detected field, update the mapping and press Save Mapping again.

8. JSON Data Contract

JSON is the boundary between MAAH SYSTEM and the renderer. The renderer does not require direct access to the upstream database as long as the exported JSON contains the fields needed by the selected template and print job.

8.1 Current test / reference job

{
  "schemaVersion": "1.0",
  "labelId": "LAB-0012",
  "brand": {
    "title": "MAAH FOOD"
  },
  "lot": {
    "lotId": "L-261006-P001-001",
    "productName": "Chicken Curry"
  },
  "product": {
    "productId": "P001",
    "productName": "Chicken Curry",
    "labelName": "Chicken Curry",
    "frozenStatus": "Tiefgefroren",
    "netWeightG": 500,
    "netWeightText": "500 g"
  },
  "print": {
    "formatCode": "L7976",
    "quantity": 10,
    "startPosition": 7,
    "labelsPerSheet": 8
  }
}

8.2 Scalar mapping rule

V1 mapping is designed for scalar values such as strings and numbers. Objects and arrays are not exposed as direct text values. If a future label needs a formatted ingredient list or similar composite value, the upstream data contract should normally provide a ready-to-render scalar text field rather than asking the SVG renderer to reconstruct business logic.

8.3 Print defaults loaded from JSON

The GUI attempts to load these values when present:

print.formatCode
print.quantity
print.startPosition

They remain visible and can be reviewed before generation.

9. Mapping System

Mapping direction is always:

SVG dynamic text ID  →  JSON path

Example:

field_product_name   → product.labelName
field_frozen_status  → product.frozenStatus
field_net_weight     → product.netWeightText

9.1 Persistent structure

{
  "schemaVersion": "1.0",
  "templates": {
    "front_default.svg": {
      "field_product_name": "product.labelName",
      "field_frozen_status": "product.frozenStatus",
      "field_net_weight": "product.netWeightText"
    }
  }
}

9.2 Why mapping is separate from the SVG

Keeping mapping outside the source artwork allows designers to work with reusable SVG templates without embedding MAAH data-path knowledge into visible design content. It also lets mapping be changed without editing the SVG file itself.

9.3 Mapping validation

Before generation, V1 checks that:

  • every detected dynamic SVG field has a mapping;
  • the mapping does not point to unknown dynamic IDs;
  • each mapped JSON path exists;
  • the resolved value is suitable as a scalar text value;
  • required values are not silently treated as valid when unusable.

10. Artwork Settings: Factory, Global and Template Defaults

The visual-settings hierarchy is:

Artwork-specific defaults ↓ if no override exists Global user defaults ↓ if settings storage is unavailable / invalid Factory defaults

10.1 Factory defaults

Artwork Scale: 95.0%
Background:    #FFFFFF
Bleed:         1.0 mm

Factory values are hardcoded in template_settings_store.py. They are the final internal fallback and can still be loaded even if the editable settings JSON is unavailable.

10.2 Global defaults

Global defaults live in template_settings.json and are used by every SVG template that does not have its own artwork-specific override.

10.3 Artwork-specific defaults

A template can override Scale / Background / Bleed. The override is keyed by template filename and therefore has priority whenever that artwork is selected.

10.4 Working settings file

{
  "schemaVersion": "1.0",
  "global": {
    "artworkScalePct": 95.0,
    "backgroundColor": "#FFFFFF",
    "bleedMm": 1.0
  },
  "templates": {
    "maah_front.svg": {
      "artworkScalePct": 88.0,
      "backgroundColor": "#E8DCCB",
      "bleedMm": 1.5
    }
  }
}

10.5 Button semantics

SAVE = persistent write USE = temporary read into GUI REMOVE = persistent delete of one artwork override FACTORY = temporary load of internal fallback values
Use Global Defaults never deletes the selected artwork override. It only places the global values into the current GUI fields. The saved artwork override remains available through Use Artwork Defaults unless explicitly removed with Remove Artwork Defaults.

10.6 Known-good default file

template_settings.default.json is the recovery baseline:

{
  "schemaVersion": "1.0",
  "global": {
    "artworkScalePct": 95.0,
    "backgroundColor": "#FFFFFF",
    "bleedMm": 1.0
  },
  "templates": {}
}

This recovery file and the internal hardcoded Factory Defaults deliberately begin with the same values, but they are different mechanisms: one is an external known-good file and the other is a code-level fallback.

Geometry describes the physical label sheet. Calibration corrects the behavior of a specific printer/setup. Default calibration can be stored in the format, while the GUI allows temporary per-run overrides.

12. Rendering & Physical Layout

12.1 Uniform artwork scaling

BaseSize = min(LabelWidth, LabelHeight)
ArtworkSize = BaseSize × ArtworkScalePct / 100

ArtworkX = LabelX + (LabelWidth - ArtworkSize) / 2
ArtworkY = LabelY + (LabelHeight - ArtworkSize) / 2

Artwork is never stretched non-uniformly. A square master remains square. Values above 100% are allowed, and artwork is clipped to the nominal label area.

12.2 Background and bleed

BackgroundX = LabelX - Bleed
BackgroundY = LabelY - Bleed
BackgroundW = LabelWidth  + 2 × Bleed
BackgroundH = LabelHeight + 2 × Bleed

Bleed affects only the generated solid background. All backgrounds are inserted before artwork so that an overlapping bleed area cannot paint over a neighboring label's artwork.

12.3 A4 coordinate system

Sheet SVGs use A4 physical dimensions: 210 mm × 297 mm, with an SVG viewBox of 0 0 210 297. Therefore one layout coordinate corresponds directly to one millimeter.

12.4 Printer calibration

X = MarginLeft + OffsetX + Column × (PitchX + PitchXAdjust)
Y = MarginTop  + OffsetY + Row    × (PitchY + PitchYAdjust)

Offset corrects constant global displacement. Pitch adjustment corrects an error that grows progressively from one row/column to the next. They solve different physical problems and should not be used interchangeably.

12.5 Start position and multi-page planning

The first page can begin on a partially used sheet. Example: L7976, quantity 10, start position 7 results in page 1 using slots 7–8 and page 2 using slots 1–8.

12.6 Output naming

Base filename:

lotId__labelId__role

Example:

L-261006-P001-001__LAB-0012__test.svg
L-261006-P001-001__LAB-0012__test__L7976__page_01.svg
L-261006-P001-001__LAB-0012__test__L7976__page_01.pdf

The role is derived from the first filename segment before the first underscore.

Final PDFs must be printed at 100% / Actual Size. Do not use Fit to Page, Shrink, Scale to Printable Area or other printer-driver scaling if physical Avery alignment matters.

16.3 What is intentionally not copied to Dist

These remain project-root maintenance tools rather than production-distribution tools.

16.4 Build procedure

  1. Close MAAH Label Renderer.exe before rebuilding; Windows locks an open executable and can prevent dist/ deletion.
  2. Run build.bat.
  3. If an existing production input/ folder is found, choose Keep or Restore.
  4. If an existing production templates/ folder is found, choose Keep or Restore.
  5. Wait for PyInstaller to finish.
  6. The final distribution folder is opened automatically.
  7. Run a production smoke test from the EXE, not only from python app.py.
If a build fails with PermissionError: [WinError 5] Access is denied inside dist\MAAH Label Renderer, first verify that the standalone application is closed. An open EXE commonly keeps the old distribution folder locked.

16.5 Windows icon cache

Windows Explorer can display an old icon for a rebuilt EXE even when PyInstaller embedded the correct icon. Renaming the EXE and seeing the correct icon confirms that the executable itself is correct and Explorer is showing cached metadata. This is not an application or build defect.

17. Recovery & Known-Good Defaults

17.1 Label formats

label_formats.default.json ↓ reset_label_formats.bat label_formats.json ↓ validate_label_formats.bat / validate_label_formats.py Validated working geometry

17.2 Artwork settings

template_settings.default.json ↓ reset_template_settings.bat template_settings.json ↓ Global = 95 / #FFFFFF / 1.0 Templates = none
Recovery reset scripts are destructive by design. They replace working configuration with the known-good default version. Back up custom settings before running a reset if those settings must be retained.

17.3 Why both code-level Factory Defaults and a default JSON exist

template_settings.default.json is an external recovery reference. Hardcoded Factory Defaults in Python are a final runtime fallback. Keeping both prevents one corrupted editable settings file from becoming a single point of failure.

18. Recommended Production Workflow

  1. Export or place the normalized label-job JSON in input/.
  2. Ensure the approved SVG template is in templates/.
  3. Open MAAH Label Renderer.
  4. Select the JSON. The browser should start in input/.
  5. Select the SVG. The browser should start in templates/.
  6. Review detected dynamic SVG IDs and Value Preview.
  7. If the template is new or changed, create/review its mapping and press Save Mapping.
  8. Confirm whether the artwork-specific or Global Scale / Background / Bleed values are correct.
  9. Confirm the Avery format, displayed dimensions, quantity and start position.
  10. Use Offset/Pitch adjustments only when a physical calibration test requires them.
  11. Press Validate.
  12. Resolve every validation error rather than bypassing it.
  13. Press Generate Labels.
  14. Review the generated sheet SVG/PDF in output/.
  15. Print at 100% / Actual Size.
  16. For a new printer, label stock or format, perform a physical alignment test before production volume.

20. Maintenance Rules

The following rules should be treated as architecture constraints unless a later version deliberately changes them:

  • Do not add a direct Python-to-Google-Sheets dependency to V1.
  • Do not treat 512 SVG units as millimeters or physical pixels.
  • Do not change square artwork into Avery-sized source artwork.
  • Do not introduce non-uniform artwork stretching.
  • Do not bake background/bleed into the master artwork as a requirement.
  • Do not hardcode individual dynamic fields in Python; detection remains field_*-based.
  • Do not mix SVG mapping with visual artwork settings.
  • Do not mix Avery geometry with template design.
  • Do not silently persist temporary GUI calibration changes.
  • Do not delete production mappings.json, template_settings.json or output/ during a normal build.
  • Do not move only the PyInstaller EXE out of its onedir distribution.
  • Do not add new V1 functionality without a concrete operational need; preserve a stable production baseline.

21. V1 Boundaries

The following are intentionally outside the current V1 scope:

  • Direct Google Sheets, Apps Script, Odoo or ERP connectivity.
  • Graphical drag-and-drop label design.
  • Automatic modification of master SVG templates.
  • Non-uniform artwork stretching.
  • Automatic text fitting, font-size reduction or sophisticated text wrapping.
  • Complex renderer-generated gradients or design effects.
  • Automatic multi-page PDF merging.
  • Database-backed job history inside the renderer.
  • Bundling Inkscape into the PyInstaller package.
  • Installer deployment into protected Program Files locations.

These limitations are deliberate. V1 is optimized for a controlled internal production workflow with low complexity, predictable files and transparent failure modes.
